## 1. ReTool 的动机：让模型学会何时停止“心算”

### 1.1 ReTool 要解决的不是“模型不会写 Python”

经过预训练或指令微调的语言模型通常已经能生成 Python 代码。真正困难的是策略问题：

- 当前步骤是否值得调用工具？
- 应该把哪一部分计算交给工具？
- 一次调用能否解决，还是需要根据结果继续调用？
- 工具返回结果后，怎样把它用于后续推理？
- 什么时候应该停止调用并给出最终答案？

因此，ReTool 学习的核心不是单个代码知识点，而是一个贯穿整条推理轨迹的**战略性工具使用策略**。

### 1.2 Long CoT 提升了推理长度，却没有消除计算脆弱性

Long Chain-of-Thought 允许模型写出更长的分析过程，适合拆解证明、规划搜索和组织多步推理。但是，语言模型的下一个 token 预测机制并不等同于可靠的数值计算器或程序执行器。

在下面这些任务中，纯文本推理很容易出现局部错误：

- 大整数或高精度运算；
- 高次方程求根；
- 大量候选的枚举与筛选；
- 递推、模拟和组合计数；
- 需要反复验证中间结果的计算。

一个局部算术错误可能污染后续整条推理链。模型即使拥有正确的解题思路，也可能因为中间数字算错而得到错误答案。

可以把这种能力边界概括为：

> Long CoT 擅长把问题“想清楚”，代码执行器擅长把明确的计算“算准确”。

ReTool 希望模型学会在两者之间动态分工。

### 1.3 固定工具规则为什么不够

最直接的方案是人为规定“遇到数学题就调用 Python”，但它存在三个问题。

第一，简单推理也调用工具会增加延迟、token 和执行成本。第二，调用工具本身并不保证有用，模型可能写出错误、超时或与当前问题无关的代码。第三，不同题目需要工具介入的时机不同，固定规则无法覆盖复杂轨迹。

另一个方案是用 SFT 模仿带工具调用的示范轨迹。它能教会模型调用格式和常见模式，但模型主要学习“像示范答案一样行动”。如果训练示范没有覆盖新题型，模型仍可能不知道何时调用最合适。

因此，ReTool 把问题改写为强化学习问题：让模型尝试不同的推理与工具调用轨迹，再根据最终解题结果调整这些轨迹的生成概率。

### 1.4 ReTool 的核心训练设定

对于同一道题，模型可以生成不同轨迹：

```text
题目
→ 文本推理
→ 可选的代码调用
→ 工具返回 observation
→ 继续文本推理或再次调用工具
→ 最终答案
```

训练时不预先规定必须调用几次工具，也不直接奖励“调用了 Python”。系统主要检查最终答案是否正确。成功轨迹中的推理和工具行为会被提高概率，失败轨迹中的行为会被降低概率。

这带来 ReTool 的两个关键设计，后续两节会分别展开：

1. **Code-interlaced rollout**：允许模型生成、工具执行和继续生成交替发生。
2. **Outcome-only reward**：主要按最终答案是否正确评分，而不是人工标注每一次工具调用。

### 1.5 “工具策略涌现”具体指什么

如果训练有效，模型可能逐渐学会：

- 简单推导直接用文本完成；
- 容易算错的计算交给 Python；
- 代码报错后修改代码并重试；
- 从 stdout 中提取结果，而不是忽略 observation；
- 得到足够信息后停止调用并输出最终答案。

这些行为不是由一条“何时使用工具”的人工规则逐项指定，而是在最终结果奖励下，由大量轨迹的相对成败共同塑造出来的。这就是这里所说的策略涌现。

需要注意：**工具调用次数增加不等于策略变好**。真正的目标是最终正确率提高。无效调用、过度调用和错误代码都可能增加调用次数，却不能证明模型学会了战略性工具使用。

### 1.6 本节结论

ReTool 的问题定义可以压缩为一句话：

> 给语言模型一个可在推理中使用的代码执行器，并通过最终答案反馈，让它学会何时调用、调用什么以及如何利用返回结果。

因此，理解 ReTool 时要区分三个层次：

1. **能力层**：模型会生成代码；
2. **交互层**：模型能调用工具、读取结果并继续生成；
3. **策略层**：模型能为了提高最终正确率而选择合适的调用时机和内容。

ReTool 真正关注的是第三层，第二层则由下一节的 code-interlaced rollout 提供实现基础。

## 2. Code-interlaced rollout：把模型生成与代码执行交织成一条轨迹

### 2.1 Rollout 是什么

在强化学习中，rollout 可以理解为策略与环境交互得到的一条完整轨迹。普通数学推理的轨迹通常很简单：

```text
题目 prompt → 模型生成一段回答 → 轨迹结束
```

ReTool 的环境中多了代码解释器。模型可以在最终回答之前多次调用它，因此一条轨迹会包含多个 assistant 回合和 tool observation：

```text
题目 prompt
→ assistant 推理并发起工具调用
→ 环境执行代码并返回 observation
→ assistant 读取 observation 后继续推理
→ assistant 给出最终答案
→ 轨迹结束
```

“Code-interlaced”强调的就是：代码不是在完整回答生成以后统一执行，而是嵌入生成过程。模型可以看到本次执行结果，再决定下一步行动。

### 2.2 一条具体轨迹

假设题目需要计算大量候选中满足某个条件的数量。一条简化轨迹可能是：

```text
user:
  求满足条件 C 的整数数量。

assistant 第 1 轮：
  先分析条件，并生成一次 code_interpreter 调用：
  count = sum(1 for x in range(...) if C(x))
  print(count)

tool observation：
  137

assistant 第 2 轮：
  根据枚举结果检查边界条件，发现还需排除两个特殊值，
  因此最终答案为 \boxed{135}。
```

这里包含两次 assistant 动作和一次环境反馈。第二轮生成依赖第一轮代码结果，所以不能把两个 assistant 回合看成互不相关的样本。

### 2.3 状态、动作与 observation

可以用强化学习的语言描述每个回合：

- **状态**：当前完整上下文，包括题目、之前的 assistant 输出和工具返回；
- **动作**：assistant 本轮生成的 token 序列；
- **环境转移**：如果动作包含合法工具调用，沙箱执行代码；
- **observation**：沙箱返回的 stdout、stderr、超时或报错信息；
- **终止动作**：assistant 不再调用工具，而是输出最终回答。

最关键的边界是：

> 工具调用代码是模型生成的动作；工具执行结果是环境提供的 observation。

例如，模型生成的 `print(2 + 3)` 属于可训练动作，而工具返回的 `5` 不是模型选择出来的 token。后续训练必须保留这个区别。

### 2.4 为什么 observation 必须进入上下文

代码工具只有在模型能读取结果时才有意义。每次执行后，observation 都要拼入下一轮 prompt，使模型能够：

- 使用正确的计算结果继续推导；
- 发现异常输出或代码错误；
- 修改代码后再次调用；
- 判断已有信息是否足够回答问题。

因此 observation 虽然不是模型动作，却会改变下一轮的状态和条件概率：

```text
下一轮动作概率 = π(assistant 输出 | 题目 + 历史动作 + tool observation)
```

如果不把 observation 放回上下文，工具调用就退化成“执行了但看不到结果”的无效行为。

### 2.5 为什么 observation 不应参与策略 loss

训练的目标是调整模型实际做出的选择。assistant token 由策略采样，具有对应的生成概率；observation token 由外部执行器产生，模型没有选择它们。

如果把 observation 也当成动作参与 loss，就相当于要求模型为环境输出负责。例如工具返回 `137`，训练却去提高或降低模型“生成 token 137”的概率，这在因果关系上是错误的。

本项目因此采用以下边界：

```text
assistant completion token：参与策略优化
tool observation token：保留在上下文中，但训练信号置 0
prompt 与历史 token：只提供条件，不作为本轮新动作训练
```

具体怎样把轨迹级 advantage 分配到 token、又怎样把 observation 区间置零，将在 GRPO 与训练 loss 部分继续展开。

### 2.6 轨迹状态机如何运行

一条轨迹的控制流程可以概括为：

```text
准备当前 prompt
→ 采样 assistant completion
→ 解析输出
   ├─ 合法工具调用：执行代码 → 拼入 observation → 进入下一轮
   ├─ 普通最终回答：记录 final_text → 结束
   └─ 非法输出或达到预算上限：结束
```

本项目还设置了硬预算，防止轨迹无限增长：

- 每条轨迹最多 4 次代码调用；
- 最多 6 个 assistant 回合；
- 整条轨迹最多 8192 tokens；
- assistant 单轮最多生成 1024 tokens；
- 单次工具返回最多保留 512 tokens。

这些限制属于 rollout 环境的一部分。它们不仅影响计算成本，也会影响模型能够探索到的策略空间。

### 2.7 同题多轨迹如何分叉

为了给后续 GRPO 提供组内比较，同一道题会采样多条轨迹。本项目默认 group size 为 8。

首轮可以从相同 prompt 一次采样出 8 个候选。此后，各轨迹可能调用不同代码、收到不同 observation，并在不同轮次结束，所以必须分别推进：

```text
同一道题
├─ 轨迹 1：纯文本回答
├─ 轨迹 2：调用一次代码后答对
├─ 轨迹 3：代码报错，修改后再次调用
└─ ……共 8 条轨迹
```

代码解释器通常是确定性环境，但轨迹仍会分化，因为模型采样出的推理、代码和调用时机不同。

### 2.8 为什么必须使用真实采样 token 续写

模型采样时会得到真实的 completion token 序列及其旧策略 log probability。工具返回后，下一轮 prompt 应在这段真实 token 后追加 assistant 结束标记和 observation token。

不能采用下面这条看似方便的路线：

```text
采样 token → 解码成文本 → 重新套 chat template → 再编码成 token
```

原因是 token 解码与重新编码不一定严格可逆，chat template 还可能清理空格、拆分 reasoning/content 或改写特殊标记。一旦重编码后的 token 与原采样 token 不同，保存的旧 log probability 就会与训练 token 错位，破坏后续 PPO 概率比值的计算。

本项目采用 **token-in token-out**：

```text
previous_prompt_tokens
+ 真实 completion_tokens
+ 尚未包含的 assistant 结束 token
+ tool observation tokens
= 下一轮 prompt_tokens
```

这不只是工程优化，而是保证“采样时记录的动作”和“训练时更新的动作”保持一致的正确性要求。

### 2.9 本节结论

Code-interlaced rollout 为 ReTool 提供了可学习的交互轨迹：模型生成工具调用，环境执行代码并返回 observation，模型再基于新状态继续行动。

理解这一机制要记住三点：

1. 一条轨迹可以包含多个 assistant 动作，而不是一次性生成；
2. observation 影响后续生成，但它本身不是模型动作；
3. 多轮续写必须保留真实采样 token，才能维持 token、旧 log probability 与训练目标的对齐。

至此我们只说明了“轨迹如何产生”。下一节要回答的是：整条轨迹完成后，系统怎样只看最终答案给出 outcome-only reward。

## 3. Outcome-only reward：只根据最终答案评价整条轨迹

### 3.1 从轨迹到一个标量分数

Code-interlaced rollout 结束后，我们得到一条可能包含多轮推理、多次代码调用和若干 observation 的完整轨迹。强化学习需要把这条轨迹的结果转换成训练信号。

设一条完整轨迹为 `τ`，参考答案为 `y*`，模型最终回答为 `y(τ)`。本项目采用二值结果奖励：

```text
R(τ) = +1    最终答案与参考答案数学等价
R(τ) = -1    最终答案错误、缺失或格式非法
```

这里的 reward 属于整条轨迹，而不是某一个回合或某一个 token。无论轨迹调用了零次、一次还是多次工具，评分器最终都只产生一个标量。

### 3.2 “Outcome-only”排除了哪些奖励

Outcome-only 的重点不仅是“奖励最终答案”，还意味着不直接给下面这些中间行为加分：

- 是否调用了代码工具；
- 工具调用次数；
- 工具调用格式是否合法；
- Python 是否成功运行；
- 中间推导是否像人工标准解；
- 代码是否简洁；
- 某个 observation 是否被正确引用。

这些指标可以记录下来做诊断，但不直接组成 reward。

例如，两条轨迹都得到正确答案：

```text
轨迹 A：纯文本推理 → 正确答案
轨迹 B：调用两次代码 → 正确答案
```

在纯 outcome-only 设定下，它们都获得 `+1`。评分器不会因为轨迹 B 使用了工具就额外加分，也不会因为轨迹 A 更短就额外奖励。

### 3.3 本项目如何判定最终答案

本项目不是简单比较两个字符串，而是采用以下步骤：

```text
取最终回答末尾 300 个字符
→ 找到最后一个 \boxed{...}
→ 提取花括号内的答案
→ 用 math_verify 与参考答案做数学等价判定
→ 正确记 +1，否则记 -1
```

只检查末尾窗口，是为了把判定集中在最终作答区域。提取最后一个 `\boxed{}`，则允许模型在前文讨论候选答案，但以最后正式提交的答案为准。

数学等价判定比字符串相等更合理。例如，在判定器能够正确解析的前提下，下面的表达可能代表同一个答案：

```text
1/2
0.5
\frac{2}{4}
```

如果找不到完整的 `\boxed{...}`、花括号没有闭合、表达式无法解析，或者数学上不等价，都得到 `-1`。

### 3.4 Format 是诊断指标，不是独立奖励

需要严格区分三个概念：

| 情况 | valid_format | correct | reward |
| --- | --- | --- | ---: |
| `\boxed{42}`，且参考答案是 42 | 是 | 是 | +1 |
| `\boxed{41}`，但参考答案是 42 | 是 | 否 | -1 |
| 最终答案写成 42，没有 `\boxed{}` | 否 | 否 | -1 |
| 代码执行成功，但最终答案错误 | 取决于最终格式 | 否 | -1 |

`valid_format` 被单独记录，是为了观察模型是否学会提交可判定答案，但它没有额外的正奖励。因此：

> 格式正确只是获得正确奖励的必要条件之一，不代表答案正确。

### 3.5 最终奖励怎样影响前面的工具行为

虽然 reward 只在轨迹结束后得到，它会通过后续计算出的 advantage 作用于轨迹中所有由 assistant 生成的动作 token。

一条答对的轨迹可能包含：

```text
分析问题
→ 决定调用工具
→ 生成 Python 代码
→ 读取 observation
→ 修正推理
→ 输出最终答案
```

评分器不知道其中哪一个局部动作最关键，只知道整条组合最终成功。训练会整体提高成功轨迹中 assistant 动作的相对概率。相反，失败轨迹中的动作组合会被相对压低。

需要再次强调：tool observation 不是 assistant 动作。它虽然属于成功轨迹的上下文，但不会因为最终 reward 为正就被当作模型输出训练。

### 3.6 为什么不用人工规定“正确的工具策略”

如果人为设计过程奖励，可能会写出类似规则：

```text
合法调用工具：+0.1
代码运行成功：+0.1
调用次数不超过两次：+0.1
最终答案正确：+1
```

这种 reward shaping 提供了更密集的反馈，却也把设计者的偏好写进了目标。模型可能为了稳定获得 `+0.1` 而频繁调用无用代码，或者为了少调用而放弃真正有帮助的计算。

Outcome-only reward 的优点是目标直接：训练目标与任务真正关心的最终正确率一致。它允许不同题目形成不同策略，也允许模型发现设计者没有预先想到的工具使用方式。

### 3.7 Outcome-only reward 的代价

纯结果奖励并不完美，它至少有四个限制。

#### 1. 信号稀疏

一条很长的轨迹直到结束才知道成败。模型得不到“前半段正确、最后一步算错”这样的局部反馈。

#### 2. 信用分配粗糙

答对时，轨迹中的有用动作和多余动作都共享成功结果；答错时，正确的中间推理也会和真正的错误步骤一起承受负向信号。

#### 3. 容易出现无区分组

如果同一道题采样出的轨迹全部答对或全部答错，它们的 reward 完全相同。组内相对比较无法判断哪条更好，后续 advantage 可能全部为零。

#### 4. 不直接约束成本

如果两条轨迹都答对，调用四次工具和不调用工具在 reward 上没有区别。调用次数、延迟和执行成本只能通过轨迹预算、数据分布或额外奖励设计间接控制。

因此，outcome-only 的成立依赖足够的探索：同一道题最好能采样到既有成功又有失败的轨迹，才能产生有方向的相对训练信号。

### 3.8 为什么不能直接把 `+1/-1` 当作更新方向

看到正确轨迹得 `+1`、错误轨迹得 `-1`，很容易以为训练会机械地“提高所有正确轨迹概率、降低所有错误轨迹概率”。但 ReTool 使用的是同题组内相对优化。

真正进入 PPO 的不是原始 reward，而是由同一道题多条轨迹的 reward 计算出的 advantage：

```text
原始结果 reward
→ 与同题其他轨迹比较
→ 得到组内 advantage
→ 用 advantage 决定概率更新方向和强度
```

这样可以减少不同题目难度造成的干扰。例如，在一道很难的题上，少数成功轨迹应当相对同组失败轨迹得到强正信号；在一道所有轨迹都能答对的简单题上，则没有必要继续强化某一条偶然采样。

### 3.9 本节结论

Outcome-only reward 把复杂的多轮工具轨迹压缩成一个最终结果判断：

> 不规定怎样使用工具，只判断整条轨迹最后有没有解决问题。

它的优势是目标直接、减少人工过程规则，并为工具策略涌现留下空间；代价是反馈稀疏、信用分配粗糙，而且依赖同题多样采样产生可比较的成败结果。

下一节将具体推导：同一道题的多条 `+1/-1` reward，怎样转换成 GRPO 组内 advantage。

## 4. GRPO 组内 advantage：用同题轨迹互相比较

### 4.1 Reward 与 advantage 不是同一个概念

Reward 是评分器对结果的直接评价。本项目中，最终答案正确得到 `+1`，否则得到 `-1`。

Advantage 回答的是另一个问题：

> 这条轨迹相对于一个基线，表现得更好还是更差？

如果 advantage 为正，后续优化倾向于提高这条轨迹中 assistant 动作的概率；如果为负，则倾向于降低；如果为零，则没有方向性训练信号。

因此数据流是：

```text
最终答案 → reward → 组内比较 → advantage → PPO loss
```

PPO 不直接使用“是否答对”这个布尔值，而是使用计算后的 advantage 决定更新方向和强度。

### 4.2 为什么需要基线

如果直接用原始 reward 更新，所有正确轨迹都被提高概率，所有错误轨迹都被降低概率，却没有考虑题目难度。

不同数学题的难度差异很大：

- 简单题可能 8 条轨迹全部答对；
- 中等题可能 8 条中答对 4 条；
- 难题可能只有 1 条偶然找到正确策略。

同一个 `+1` 在不同题目中的信息量并不相同。在简单题上，正确可能只是模型的常规表现；在极难题上，少数正确轨迹可能包含很有价值的探索结果。

传统 actor-critic 方法通常训练一个 value model 估计基线。GRPO 的核心思路是：对同一道题一次采样多条回答，用这一组回答的平均表现构造相对基线，从而不需要额外训练 critic。

### 4.3 本项目的组内中心化公式

设同一道题采样 `G` 条轨迹，第 `i` 条轨迹的 reward 为 `r_i`。先计算组内平均 reward：

```text
r_mean = (r_1 + r_2 + ... + r_G) / G
```

然后计算每条轨迹的 advantage：

```text
A_i = r_i - r_mean
```

本项目默认 `G = 8`，实现使用的就是上述“减去同题组平均 reward”的中心化形式。

它有一个直接性质：

```text
A_1 + A_2 + ... + A_G = 0
```

也就是说，组内正负信号天然平衡。训练关注的是哪些轨迹相对同题的其他轨迹更好，而不是让某一道题整体产生持续的正向或负向偏移。

### 4.4 例一：8 条轨迹中只有 2 条答对

假设 reward 为：

```text
[+1, +1, -1, -1, -1, -1, -1, -1]
```

组均值是：

```text
r_mean = (2 × 1 + 6 × -1) / 8 = -0.5
```

因此：

```text
正确轨迹：A = +1 - (-0.5) = +1.5
错误轨迹：A = -1 - (-0.5) = -0.5
```

这时正确轨迹非常稀少，所以它们获得较强的正 advantage；单条错误轨迹只获得较弱的负 advantage。

### 4.5 例二：8 条轨迹中有 6 条答对

假设 reward 为：

```text
[+1, +1, +1, +1, +1, +1, -1, -1]
```

组均值为：

```text
r_mean = (6 × 1 + 2 × -1) / 8 = +0.5
```

因此：

```text
正确轨迹：A = +1 - 0.5 = +0.5
错误轨迹：A = -1 - 0.5 = -1.5
```

大多数轨迹已经能答对时，普通正确轨迹不再稀有，只得到较弱正信号；少数失败轨迹则明显落后于同组，得到较强负信号。

两个例子共同说明：

> Advantage 的大小不仅取决于自身 reward，还取决于同题其他轨迹的表现。

### 4.6 二值奖励下的一般规律

设 `G` 条轨迹中有 `m` 条正确，则组均值为：

```text
r_mean = [m × (+1) + (G-m) × (-1)] / G
       = 2m/G - 1
```

正确与错误轨迹的 advantage 分别为：

```text
A_correct = +1 - r_mean = 2(G-m)/G
A_wrong   = -1 - r_mean = -2m/G
```

由此可以看到：

- 正确样本越少，单条正确轨迹的正 advantage 越大；
- 错误样本越少，单条错误轨迹的负 advantage 绝对值越大；
- 组内越接近全对或全错，少数派轨迹携带的相对信息越强。

### 4.7 Degenerate group：为什么全对或全错没有梯度

如果 8 条轨迹全部正确：

```text
r_mean = +1
A_i = +1 - 1 = 0
```

如果 8 条轨迹全部错误：

```text
r_mean = -1
A_i = -1 - (-1) = 0
```

两种情况的所有 advantage 都是零，这类组称为 degenerate group，即组内没有可用于排序的差异。

这不是程序故障，而是相对优化的自然结果：

- 全对时，当前组无法告诉模型哪条正确轨迹更值得偏好；
- 全错时，当前组也无法提供一个相对成功的方向。

本项目会统计 `degenerate_group_rate`。如果该比例长期过高，有效训练数据就会减少；若整个 rollout batch 都没有非零 advantage，本次参数更新会被跳过。

### 4.8 为什么同组必须来自同一道题

假设把一道简单题的正确轨迹与一道极难题的错误轨迹直接比较，得到的相对结果主要反映题目难度，而不一定反映策略质量。

同题分组尽量固定了问题条件：

```text
相同题目 + 相同参考答案 + 相同工具环境
→ 不同采样轨迹
→ 比较不同动作序列的最终结果
```

这样，reward 差异更可能来自模型采样出的推理过程、工具调用时机和代码内容，而不是题目本身的难度差异。

### 4.9 标准 GRPO 常见公式与本项目实现的区别

标准 GRPO 的介绍中经常见到标准化 advantage：

```text
A_i = (r_i - r_mean) / (r_std + ε)
```

除了减去均值，它还除以组内标准差，使不同组的 advantage 尺度更加接近。

本项目实际实现为：

```text
A_i = r_i - r_mean
```

即只做组内中心化，不除以标准差。因此阅读代码和实验时，应准确称为“GRPO 风格的组内中心化 advantage”，不要误以为项目实现了所有常见 GRPO 细节。

两者的更新方向通常一致，但数值尺度不同。只中心化会保留当前组正确率对 advantage 幅度的影响；标准化则进一步消除这种尺度差异。

### 4.10 轨迹 advantage 如何落到 token 上

本项目先为整条轨迹计算一个 advantage，再把它赋给该轨迹所有 assistant completion token：

```text
题目与历史 prompt token：advantage = 0
assistant 第 1 轮 token：advantage = A_trajectory
tool observation token：advantage = 0
assistant 第 2 轮 token：advantage = A_trajectory
……
```

例如某条轨迹的 advantage 是 `+1.5`，那么它生成的分析文字、工具调用代码和最终答案 token 都使用 `+1.5`；夹在中间的工具返回仍然为零。

这体现了 outcome-only 的粗粒度信用分配：训练知道整条 assistant 动作序列相对成功，却不知道成功应精确归因于哪一个 token。

### 4.11 GRPO advantage 与 PPO 的分工

GRPO 组内比较解决的是：

```text
哪条轨迹应该提高概率，哪条应该降低概率，信号有多强？
```

PPO clip 解决的是：

```text
按照这个方向更新时，一次最多允许策略改变多大？
```

因此二者不是互斥算法。在本项目中可以理解为：

```text
Outcome-only reward 提供结果
→ GRPO 组内中心化提供 advantage
→ PPO clipped loss 执行受约束的策略更新
```

### 4.12 Group size 的影响

Group size 决定每道题用于相对比较的轨迹数量。

较大的 group：

- 更容易同时采到成功与失败轨迹；
- 组均值更稳定；
- 能看到更多不同工具策略；
- 但 rollout 成本更高。

较小的 group：

- 采样成本较低；
- 但均值波动更大；
- 更容易出现全对或全错；
- 对稀有成功策略的发现能力较弱。

本项目使用 group size 8，是训练信号稳定性与采样成本之间的工程折中；论文完整方案使用更大的每题采样数，差异将在最后一节统一比较。

### 4.13 本节结论

GRPO 组内 advantage 把绝对的最终结果转换成同题内的相对训练信号：

> 一条轨迹是否值得强化，不只看它答没答对，还看它相对于同一道题的其他采样表现如何。

本项目的精确计算是 `A_i = r_i - r_mean`。混合成败的组能够产生正负信号；全对或全错的组 advantage 全零。轨迹 advantage 随后只分配给 assistant 生成 token，tool observation 保持为零。

下一节将进入 PPO clip，解释 advantage 如何与新旧策略概率比结合，并限制单次参数更新幅度。

## 5. PPO clip：限制一次策略更新走得太远

### 5.1 Advantage 只给出了方向

上一节得到的 advantage 告诉我们：

- `A > 0`：这条轨迹相对同组更好，应提高其中 assistant 动作的概率；
- `A < 0`：这条轨迹相对同组更差，应降低其中 assistant 动作的概率；
- `A = 0`：没有相对训练信号。

但 advantage 没有回答“单次应该改变多少”。如果模型一次更新就把成功样本概率推得极高、把失败样本概率压得极低，策略可能迅速偏离生成这些 rollout 的旧策略，导致训练不稳定或能力退化。

PPO clip 的作用就是：在沿 advantage 指示的方向更新时，限制从同一批旧数据中获得的有效改进幅度。

### 5.2 旧策略与新策略

Rollout 是由更新前的策略采样出来的，记为：

```text
π_old
```

训练过程中正在计算梯度、准备更新的策略记为：

```text
π_θ
```

对轨迹中的某个 assistant token `a_t`，其上下文状态为 `s_t`。采样时记录：

```text
log π_old(a_t | s_t)
```

训练时模型重新计算：

```text
log π_θ(a_t | s_t)
```

二者共同用于衡量当前策略相对采样策略发生了多大变化。

### 5.3 新旧概率比

PPO 使用概率比值：

```text
ρ_t(θ) = π_θ(a_t | s_t) / π_old(a_t | s_t)
```

实际计算通常使用 log probability：

```text
ρ_t(θ) = exp[log π_θ(a_t | s_t) - log π_old(a_t | s_t)]
```

比值的含义是：

| `ρ_t` | 含义 |
| ---: | --- |
| `1.0` | 新旧策略给该 token 的概率相同 |
| `1.2` | 新策略概率是旧策略的 1.2 倍 |
| `0.8` | 新策略概率是旧策略的 0.8 倍 |

这也解释了为什么 rollout 阶段必须保存真实 completion token 及其旧 log probability：没有一一对应的旧概率，就无法正确计算概率比。

### 5.4 未截断的策略目标

最简单的策略目标可以写成：

```text
L_unclipped,t = ρ_t A_t
```

如果 `A_t > 0`，增大该 token 的概率会使 `ρ_t A_t` 增大；如果 `A_t < 0`，降低该 token 的概率会使目标改善。

问题在于，只要继续把概率向“有利方向”推动，这个目标就可能继续鼓励更新，即使新策略已经离旧策略很远。

### 5.5 PPO clipped objective

设允许的概率比区间为：

```text
[c_low, c_high]
```

先把概率比裁剪到该区间：

```text
clip(ρ_t, c_low, c_high)
```

PPO 的单 token clipped surrogate objective 为：

```text
L_clip,t = min(
    ρ_t A_t,
    clip(ρ_t, c_low, c_high) A_t
)
```

这里写的是需要最大化的目标；训练库实现为 loss 时通常会取负号再最小化。

`min` 与 advantage 的正负共同保证：模型不能因为把概率朝有利方向推得过远而继续获得更好的目标值。

### 5.6 正 advantage 时怎样截断

假设：

```text
A_t = +1.5
c_high = 1.28
```

若 `ρ_t = 1.10`，仍在区间内：

```text
ρ_t A_t = 1.10 × 1.5 = 1.65
```

若 `ρ_t = 1.30`，超过上界：

```text
未截断项 = 1.30 × 1.5 = 1.95
截断项   = 1.28 × 1.5 = 1.92
L_clip,t  = min(1.95, 1.92) = 1.92
```

继续把概率比从 `1.28` 推到 `1.30`，不会从这一项得到额外收益。它抑制的是“对好动作一次奖励过头”。

### 5.7 负 advantage 时怎样截断

假设：

```text
A_t = -0.5
c_low = 0.8
```

若 `ρ_t = 0.90`，仍在区间内：

```text
ρ_t A_t = 0.90 × -0.5 = -0.45
```

若 `ρ_t = 0.70`，低于下界：

```text
未截断项 = 0.70 × -0.5 = -0.35
截断项   = 0.80 × -0.5 = -0.40
L_clip,t  = min(-0.35, -0.40) = -0.40
```

继续把坏动作的概率比从 `0.8` 压到 `0.7`，不会从这一项获得额外收益。它抑制的是“对坏动作一次惩罚过头”。

### 5.8 正负 advantage 下的整体直觉

| Advantage | 希望的方向 | 起主要限制作用的边界 |
| --- | --- | --- |
| `A > 0` | 提高该 token 概率 | `c_high`，防止提高过多 |
| `A < 0` | 降低该 token 概率 | `c_low`，防止降低过多 |

如果策略朝错误方向变化，PPO 不会用 clip 帮它“免除惩罚”。例如正 advantage token 的概率大幅下降，未截断目标会变差；负 advantage token 的概率大幅上升，同样会得到更差的目标。

因此 clip 主要截断的是**沿正确更新方向获得的过量收益**，不是把所有概率比无条件夹死。

### 5.9 本项目为什么是 `0.8/1.28`

本项目配置为：

```text
c_low  = 0.8
c_high = 1.28
```

它对应：

```text
ε_low  = 0.20    → 1 - ε_low  = 0.80
ε_high = 0.28    → 1 + ε_high = 1.28
```

这是一个非对称 clip 区间：

- 对负 advantage 动作，概率比向下最多在 `0.8` 处失去进一步优化收益；
- 对正 advantage 动作，概率比向上到 `1.28` 才失去进一步优化收益。

上侧空间比下侧更宽，属于 DAPO 中常见的 clip-higher 思路：允许高 advantage token 获得稍大的概率提升空间，同时仍通过截断避免无界更新。

需要注意，`1.28` 表示新旧概率之比的上侧阈值，不是“概率增加 28 个百分点”。例如旧概率为 `0.10` 时，比例 `1.28` 对应新概率约为 `0.128`，增加的是 `0.028`，而不是变成 `0.38`。

### 5.10 Clip 是软约束，不是硬限制

常见误解是：设置 `[0.8, 1.28]` 后，所有 token 的新旧概率比一定不会越界。

实际上，PPO clip 只改变目标函数：超过有利方向边界后，该样本不再提供继续越界的额外收益。它不会直接把模型参数投影回某个范围，也不能保证一次优化后每个 token 的实际概率比都严格位于区间内。

原因包括：

- 不同 token 的梯度共享同一组模型参数；
- 一个 token 的更新会间接影响其他 token；
- Adam 学习率和梯度累计也会影响最终步长；
- 不同训练样本的梯度可能互相叠加或冲突。

所以更准确的说法是：

> PPO clip 限制样本在目标函数中推动策略继续远离旧策略的激励，而不是对最终概率实施硬裁剪。

### 5.11 在 ReTool 多轮轨迹中如何使用

同一条轨迹中的所有 assistant completion token 使用相同的轨迹 advantage，但每个 token 都有自己的旧概率、新概率和概率比：

```text
轨迹 advantage A
├─ 推理 token 1：ρ_1，计算 PPO clip
├─ 推理 token 2：ρ_2，计算 PPO clip
├─ 工具调用 token：各自计算 PPO clip
├─ observation token：A = 0，不产生策略更新
└─ 最终答案 token：各自计算 PPO clip
```

因此，“整条轨迹共享一个成败信号”与“每个 token 分别限制概率变化”可以同时成立。

代码调用中的函数名、参数和 Python 代码都是 assistant 生成的 token。如果轨迹 advantage 为正，它们会与其他 assistant token 一样得到正向优化；工具返回的 stdout/stderr 则保持 advantage 为零。

### 5.12 为什么 PPO clip 对 outcome-only RL 很重要

Outcome-only reward 稀疏，少数成功轨迹可能得到较大的正 advantage。例如 8 条轨迹只有 1 条正确时，本项目的正确轨迹 advantage 为：

```text
A_correct = 2 × (8 - 1) / 8 = 1.75
```

这种稀有成功轨迹很有价值，但它也可能包含偶然因素、多余调用或碰巧正确的推理。如果没有更新约束，模型可能过度追随单批样本。

PPO clip 允许模型从稀有成功中学习，同时限制一次更新对旧策略的偏离程度。后续新的 rollout 会再次检验这种行为是否稳定带来正确答案。

### 5.13 从 rollout 到一次参数更新

本项目的一次训练 step 可以概括为：

```text
用当前采样策略生成同题多轨迹
→ 保存 assistant token 的旧 log probability
→ 按最终答案计算 +1/-1 reward
→ 计算组内中心化 advantage
→ 为每个 assistant token 计算新旧概率比
→ 应用 PPO clipped loss
→ 累积各 micro-batch 梯度
→ 整个 rollout batch 执行一次 Adam 更新
```

如果整个 batch 都来自 degenerate group，没有非零 advantage，也就没有有效 PPO 样本，本次优化器更新会跳过。

### 5.14 本节结论

PPO clip 把 GRPO advantage 转换为受约束的策略更新：

> Advantage 决定提高还是降低动作概率；概率比衡量新旧策略变化；clip 限制一次更新从同一批数据中获得的过量收益。

本项目使用非对称区间 `[0.8, 1.28]`。正 advantage token 主要受上界约束，负 advantage token 主要受下界约束。该区间约束的是优化目标，而不是对模型最终概率实施硬裁剪。

下一节将把前面几部分连起来，解释没有工具调用奖励时，工具策略为什么仍然能够从结果奖励中逐步涌现。

## 6. 工具策略如何涌现：结果选择逐步塑造中间行为

### 6.1 “涌现”不代表凭空获得能力

这里所说的工具策略涌现，是指训练没有逐条规定：

```text
遇到哪类题必须调用工具
应该在哪一步调用
应该写什么代码
调用几次后必须停止
```

但经过结果奖励训练后，模型的实际行为分布可能逐渐表现出这些规律。

它不意味着模型从零发明了 Python、工具协议或数学知识。策略涌现通常依赖基座模型已经具备若干前置能力：

- 能生成基本正确的 Python；
- 能按照工具协议发起调用；
- 能阅读 stdout、stderr 等 observation；
- 能把计算结果整合进后续推理；
- 偶尔能探索到成功的完整轨迹。

强化学习主要做的是选择和重组这些已有能力，使“对最终任务有帮助的组合”出现得更频繁。

### 6.2 没有工具奖励，为什么工具调用仍会被强化

假设同一道题采样 8 条轨迹，其中只有 2 条答对。两条成功轨迹都在关键步骤调用 Python 完成了可靠计算，其余轨迹因为纯文本算术错误或无效代码而失败。

上一节已经算出：

```text
正确轨迹 advantage = +1.5
错误轨迹 advantage = -0.5
```

PPO 会提高成功轨迹中 assistant token 的相对概率，其中包括：

- 决定调用工具前的推理 token；
- `<tool_call>` 协议 token；
- `code_interpreter` 名称与参数 token；
- Python 代码 token；
- 读取结果并修正推理的 token；
- 最终答案 token。

因此，工具调用不需要单独获得 `+0.1`。只要某类工具行为在大量样本中稳定提高最终成功概率，它就会更频繁地出现在正 advantage 轨迹中，从而被间接强化。

### 6.3 为什么无用工具行为不会必然一起强化

单条成功轨迹中的多余调用确实也会共享正 advantage，这是 outcome-only 信用分配粗糙的一面。但训练并不只看一条轨迹。

跨越许多题目和采样后，行为可能出现三种统计关系：

1. **有益行为**：更常出现在成功轨迹中，累计获得净正信号；
2. **有害行为**：更常导致报错、超时、截断或错误答案，累计获得净负信号；
3. **无关行为**：在成功与失败轨迹中近似随机出现，正负信号长期部分抵消。

所以策略涌现依赖重复采样形成统计筛选，而不是评分器在单条轨迹里准确指出“第 37 个 token 是成功关键”。

### 6.4 一条完整的学习链路

把前面五节连起来，可以得到：

```text
模型探索不同推理与工具动作
→ 沙箱返回真实 observation
→ 模型基于 observation 完成答案
→ 最终答案得到 +1/-1 reward
→ 同题轨迹比较得到正负 advantage
→ PPO 提高相对成功动作的概率并压低相对失败动作
→ 新策略再次 rollout
→ 更有效的工具行为出现得更频繁
```

关键在于这是循环过程。单次更新只能改变一点点行为概率；下一批 rollout 会重新检验这些改变是否真的提高最终正确率。

### 6.5 工具策略可能分阶段形成

对于已经具备初步代码能力的基座模型，训练常见的行为改善顺序可以分成四层。

#### 第一层：调用协议合法

模型先学会稳定生成可解析的工具调用：

```text
正确的工具名
正确的参数结构
一次 assistant 回合只提交合法调用
```

如果格式无法解析，代码根本不会执行，后续自然难以答对。

#### 第二层：代码能够执行

模型进一步减少：

- 语法错误；
- 未定义变量；
- 忘记输出结果；
- 超时枚举；
- 不符合沙箱约束的操作。

“合法调用”只表示请求能被协议识别，“代码能运行”才表示环境能够返回有用 observation。

#### 第三层：代码与问题相关

能够运行的代码不一定有助于解题。模型还要学会：

- 把正确的子问题交给代码；
- 选择合适的算法和搜索范围；
- 打印后续推理真正需要的信息；
- 检查边界和异常情况。

#### 第四层：调用时机与次数合理

成熟策略不等于一味增加 code calls，而是根据问题动态选择：

```text
简单推理：不调用
复杂计算：调用一次获得关键结果
代码报错或结果不足：修改后再次调用
信息充分：停止工具交互并作答
```

这才是“strategic tool use”中的 strategic。

### 6.6 为什么调用次数不是核心指标

平均 code calls 上升可能有多种解释：

- 模型更愿意使用有帮助的计算；
- 模型反复提交错误代码；
- 模型过度依赖工具；
- 模型学会了复杂的多阶段计算；
- 轨迹变长但最终答案没有改善。

因此必须联合观察：

```text
最终正确率
+ 合法工具调用率
+ 沙箱成功率/错误率/超时率
+ 平均调用次数与轮数
+ 轨迹截断率或格式率
```

只有当正确率改善，同时调用质量、执行成功率或任务相关性也改善，才有较强证据说明工具策略变好了。

### 6.7 Observation 在策略学习中的作用

如果模型只学会发起调用，却不会利用返回结果，那么工具仍然没有形成闭环。

有用策略通常包含条件行为：

```text
如果 observation 是正常数值
→ 将其代入后续推理

如果 observation 是异常或报错
→ 定位代码问题并修改

如果 observation 表明假设不成立
→ 更换解题路线
```

工具 observation 虽然 advantage 为零，却通过改变下一轮上下文影响后续动作。模型学习的不是“生成 observation”，而是“在看到不同 observation 时生成合适的后续动作”。

### 6.8 涌现需要哪些条件

仅有 outcome-only reward 并不保证工具策略一定出现。至少需要以下条件。

#### 1. 基座存在初始探索概率

如果模型从不生成合法工具调用，RL 就看不到使用工具的成功轨迹，也无法凭空提高它们的概率。这也是某些基座需要 cold-start SFT 的原因。

#### 2. 工具确实能提高任务成功率

任务必须包含代码执行器擅长解决的子问题。如果数据全部是简单概念问答，工具行为不会获得稳定优势。

#### 3. 同题采样具有多样性

需要在同一组中探索到不同推理和调用方式，最好同时出现成功与失败，GRPO 才能形成相对信号。

#### 4. 环境反馈可靠

沙箱必须正确执行代码、稳定返回结果并限制异常行为。错误或错位的 observation 会把噪声引入学习循环。

#### 5. 奖励判定可靠

最终答案验证器必须尽量避免误判。否则模型可能强化的是利用评分漏洞的行为，而不是真正的解题策略。

#### 6. 更新足够稳定

Token 与旧 log probability 必须对齐，observation 必须 mask，PPO 更新不能过猛。否则少量成功轨迹可能造成不稳定漂移。

### 6.9 为什么项目可以跳过 cold-start SFT

论文完整方案先用代码交织轨迹进行 cold-start SFT，目的是让模型先掌握基本交互格式和工具使用模式，再进行 outcome-only RL。

本项目的 Qwen3.5-4B 在 smoke test 中已经能够较高频率地生成工具调用，并且同题采样能出现正负 reward。这意味着：

```text
初始策略已经能探索到合法工具行为
+ 部分行为能够产生成功结果
+ GRPO group 内存在可比较差异
```

于是项目选择直接从 base model 做 RL。

这个结论只针对当前基座和协议，不应推广为“ReTool 永远不需要 SFT”。如果换一个不会原生 tool call、几乎不写代码或无法读取 observation 的模型，直接 RL 很可能因为没有初始成功轨迹而学不起来。

### 6.10 策略涌现不等于因果归因准确

Outcome-only 训练观察到的是轨迹行为与最终成功之间的相关性，而不是严格的局部因果证明。

例如一条轨迹可能：

```text
调用了一次无关代码
→ 后续纯文本推理碰巧答对
→ 整条轨迹获得正 advantage
```

这次更新也会提高无关代码 token 的概率。只有经过大量不同题目和重复采样，无关行为的正负信号才有机会抵消。

因此，判断是否真正学到工具策略，需要做超出训练 reward 的验证，例如：

- 与禁用工具的 text-only 模式比较；
- 检查调用内容是否解决了必要子问题；
- 对适合与不适合工具的题目分别统计调用率；
- 扰动或移除 observation，观察答案是否随之合理变化；
- 在未见题型上评估工具调用是否仍有效。

### 6.11 常见失败模式

#### 工具塌缩为“从不调用”

如果初始工具调用大多报错，使用工具的轨迹持续失败，模型可能快速降低调用概率，失去进一步探索机会。

#### 工具塌缩为“逢题必调”

如果训练数据中的成功轨迹普遍包含工具调用，模型可能学到“调用工具”这一表面相关性，而没有学会判断何时真正需要。

#### 学会格式但没有学会解题

模型可能显著提高合法调用率和 `\boxed{}` 格式率，但正确率提升有限。协议能力是必要条件，却不是最终目标。

#### 学会运行代码但不会使用结果

沙箱成功率提高，不代表 observation 被正确整合。模型可能打印大量内容，随后仍按原先猜测作答。

#### 奖励漏洞与偶然成功

如果答案提取或数学验证存在漏洞，模型可能优化判定器偏好；即使验证器可靠，有限采样中也可能出现碰巧正确的轨迹。

### 6.12 如何解读本项目报告的行为趋势

本项目的单次复现实验报告了大致如下的训练趋势：

```text
合法工具调用率上升
沙箱错误率下降、成功率上升
最终正确率上升
平均代码调用次数总体增加但存在波动
```

把这些指标联合起来，可以形成一种合理解释：模型先更稳定地遵守工具协议，再提高生成代码的可执行性，最终更频繁地产生对答案有帮助的工具轨迹。

但这些曲线来自单次、小规模复现，只能作为与策略涌现一致的证据，不能单独证明每一次行为变化都由某个确定机制引起，也不能等同于稳定复现论文收益。

### 6.13 本节结论

工具策略涌现的核心机制不是“调用工具有奖励”，而是：

> 如果某类工具行为能跨越大量轨迹稳定提高最终成功概率，它就会更频繁地获得正 advantage，并通过 PPO 逐步提高生成概率。

Outcome-only reward 提供最终选择标准，GRPO 提供同题相对比较，PPO clip 提供稳定更新，code-interlaced rollout 则让工具行为及其后果真实出现在轨迹中。

这种学习仍然是粗粒度、统计性的。它依赖基座能力、探索多样性、可靠环境与验证器，可能出现过度调用、从不调用或只学格式等失败模式。

下一节将比较 ReTool 论文完整方案、官方 released recipe 与本项目复现，明确哪些差异会改变算法目标，哪些主要影响训练规模和工程效率。

## 7. 论文完整方案、官方 recipe 与本项目复现的差异

### 7.1 必须区分三套对象

学习 ReTool 时容易把下面三者混在一起：

1. **论文方案**：论文正文定义的方法、训练流程和实验配置；
2. **官方 recipe**：veRL 后续发布并持续更新的工程复现；
3. **本项目复现**：为了降低成本和复杂度而实现的轻量版本。

三者共享 ReTool 的核心思想，但不保证每个超参数、奖励细节和优化算法完全一致。尤其是官方仓库会继续演化，阅读时应记录所参考的版本和日期。

本节核对的主要外部资料为：

- [ReTool 论文](https://arxiv.org/abs/2504.11536)
- [当前 veRL ReTool recipe](https://github.com/verl-project/verl-recipe/tree/main/retool)
- [当前官方 reward 实现](https://github.com/verl-project/verl-recipe/blob/main/retool/retool.py)
- [当前官方 DAPO/GRPO 配置](https://github.com/verl-project/verl-recipe/blob/main/retool/run_qwen2-32b_dapo.sh)
- [当前官方 PPO 配置](https://github.com/verl-project/verl-recipe/blob/main/retool/run_qwen2-32b_ppo.sh)

### 7.2 本项目保留了哪些 ReTool 核心

虽然规模和工程实现不同，本项目保留了四个决定 ReTool 身份的机制：

1. 推理过程中允许模型动态调用代码解释器；
2. 代码执行结果实时回填，模型可以继续推理或再次调用；
3. 最终任务结果是主要训练反馈；
4. 工具 observation 保留在上下文中，但不作为模型动作参与 loss。

因此，本项目能够复现“工具交织轨迹怎样进入 outcome-driven RL”的核心闭环：

```text
文本/代码交织 rollout
→ 最终答案 reward
→ 相对 advantage
→ clipped policy update
```

下面的差异主要决定：初始工具能力有多强、训练信号如何估计、一次实验能探索多大的策略空间，以及最终结果能否与论文数字直接比较。

### 7.3 总体对照

| 维度 | 论文方案 | 当前官方 recipe | 本项目复现 |
| --- | --- | --- | --- |
| 训练阶段 | Cold-start SFT → RL | 提供 SFT → DAPO/GRPO 或 PPO | 跳过 SFT，直接 RL |
| 主要基座 | Qwen2.5-32B-Instruct；另测 DeepSeek-R1-Distill-Qwen-32B | Qwen2.5-32B-Instruct SFT checkpoint | Qwen3.5-4B |
| 参数训练 | 大规模分布式训练 | FSDP 分布式 actor/critic 或 GRPO | LoRA rank 32 |
| Advantage/RL | 论文正文写 PPO | 同时提供 GRPO/DAPO 与 GAE-PPO | 同题组内中心化 advantage + PPO loss |
| 最长序列 | 16384 | response 16384，prompt 2048 | 整条轨迹 8192 |
| 工具轮次 | 多轮 | 最大 user/assistant turns 8 | 最多 4 次代码调用、6 个 assistant 回合 |
| 工具表示 | `<code>` / `<interpreter>` 标签 | Hermes/native function tool 接口 | Qwen 原生 `<tool_call>` |
| 沙箱 | 分布式异步沙箱池 | SandboxFusion，异步多 worker | 本地 subprocess 沙箱 |
| Observation loss | mask | 多轮工具框架负责 mask | observation advantage 显式置 0 |
| KV cache | 明确复用代码执行前 cache | 依赖 veRL/vLLM 多轮基础设施 | 未专门实现论文式复用 |
| Reward | 最终正确 `+1/-1`，不奖励可执行性 | 当前代码对错误答案加入轮次 shaping | 严格 `+1/-1`，不加 shaping |
| 训练规模 | 32B、论文主实验 400 steps | DAPO 配置 batch 512、每题 16 条 | 每步 8 题 × 8 条，最多 200 steps |
| 评测采样 | AIME2024/2025 各重复 32 次 | AIME25 每题 30 次 | AIME25 每题 12 次 |

这张表用于定位差异，不能把不同版本下的配置数字理解成严格的一一对应实验。

### 7.4 最大流程差异：跳过 cold-start SFT

论文方法由两个阶段组成。

第一阶段构造代码增强的长推理轨迹：从数学推理数据出发，把适合代码执行的手工计算替换成代码及其执行结果，再经过格式验证和答案验证，形成 cold-start 数据。论文随后用这些数据进行 SFT，让模型先学会工具调用和结果分析。

第二阶段才进行带实时代码执行的 RL，让模型在 outcome reward 下继续发展策略。

论文报告 cold-start 训练本身已经带来明显收益，说明它不仅教格式，也提供了有价值的工具推理先验。

本项目跳过这一阶段，直接从 Qwen3.5-4B 做 RL。理由不是“SFT 没用”，而是 smoke test 已经观察到：

```text
基座能够发起工具调用
+ 合法调用率足够高
+ 同题组出现正负 reward
= 已具备直接 RL 所需的初始探索条件
```

这一简化显著降低数据准备和训练成本，但也改变了初始策略分布。若换成缺乏原生工具能力的模型，可能出现工具调用迅速塌缩、长期采不到成功轨迹的问题。

### 7.5 优化算法差异：不能统称为“论文 GRPO”

ReTool 论文正文明确写的是 PPO，并给出 clipped PPO objective。论文没有把 GRPO 作为其原始训练算法。

当前官方 recipe 后续同时提供两条工程路线：

- **DAPO/GRPO 路线**：`adv_estimator=grpo`，每题采样 16 条，使用非对称 clip，并启用 `clip_ratio_c=10.0`；
- **PPO 路线**：`adv_estimator=gae`，训练 critic，用 GAE 计算 advantage，再使用 PPO clip。

本项目采用第三种轻量组合：

```text
同题 reward 减组均值
→ 得到 GRPO 风格组内中心化 advantage
→ 不训练 critic
→ 使用 PyTRIO PPO clipped loss 更新 actor
```

因此最准确的描述是：

> 本项目使用 GRPO 风格的组内 advantage 和 PPO 风格的 clipped policy loss。

它既不等同于论文的完整 PPO 训练，也不等同于当前官方 DAPO recipe。特别是，本项目没有实现官方 DAPO 配置中的 `clip_ratio_c=10.0`，也没有训练 PPO critic 或计算 GAE。

### 7.6 Reward 差异与官方代码版本漂移

论文给出的 reward 非常明确：预测答案与参考答案数学等价则 `+1`，否则 `-1`；论文还强调不加入代码可执行性奖励，以减少 reward hacking 并保留策略多样性。

当前官方 recipe 的 `compute_score` 并非严格纯二值。它先调用严格 `\boxed{}` 数学判定；若答案错误，再根据 `num_turns` 增加一个小的工具轮次 bonus，并把错误样本分数封顶在 `-0.6`：

```text
tool_call_reward = (num_turns - 2) / 2 × 0.1
wrong_score = min(-0.6, original_score + tool_call_reward)
```

这意味着两个都答错的轨迹可能因为工具轮次不同而获得不同 reward。它属于 reward shaping，与论文公式中的严格 outcome-only 不完全一致。

本项目选择：

```text
答对：+1
其他所有情况：-1
```

因此在 reward 目标上，本项目反而更接近论文公式，而不是当前官方 recipe 的 shaping 实现。

需要注意版本漂移：本地原始说明记录的官方 shaping 上限与当前 upstream 代码不同。复现实验时必须固定 commit，不能只写“使用官方 reward”而不说明具体版本。

### 7.7 工具协议差异：标签触发与原生 tool call

论文轨迹使用：

```text
<code>Python 代码</code>
<interpreter>执行结果</interpreter>
```

检测到 `</code>` 后暂停生成，执行代码，再把结果放入 `<interpreter>` 标签中继续生成。

本项目不新增这套代码标签，而是使用 Qwen 原生工具协议：

```text
assistant 生成 <tool_call>
→ code_interpreter 执行
→ role="tool" 消息返回 observation
→ assistant 继续生成
```

两种表示在功能上都能形成 code-interlaced rollout，但 token 分布和模型初始熟悉度不同。原生协议的工程优势是无需修改 tokenizer 或额外训练特殊代码边界；代价是实验不再严格复刻论文的提示格式。

当前官方 recipe 也已经通过 veRL 多轮工具接口和 Hermes 格式使用 function tool，这说明“代码块标签”不是 ReTool 核心机制不可替换的一部分。

### 7.8 沙箱与并发差异

论文为了大规模训练设计了分布式异步沙箱：多个 sandbox worker 根据容量从任务池取代码执行请求，避免慢代码阻塞整批 rollout。

当前官方 recipe 使用 SandboxFusion，并配置大量 worker、速率限制、超时和内存限制。

本项目使用本地 subprocess：

```text
每次调用启动独立 Python 进程
30 秒超时
本地并发池
stdout/stderr 截断与特殊 token 消毒
```

只要执行语义一致，本地沙箱不会改变 ReTool 的基本算法定义，但会影响：

- rollout 吞吐；
- 资源隔离强度；
- 超时和异常分布；
- 可承载的训练并发；
- Windows、Linux 等平台兼容性。

本项目沙箱的文件访问限制部分依赖提示词和进程约束，不能视为与生产级远程沙箱等价。

### 7.9 KV cache 与 token 续写

论文明确实现 KV-cache reuse：模型生成到代码结束标记时，保留代码执行前的 KV cache；工具返回后，只对新增 interpreter feedback 计算增量 cache，从而减少多轮 rollout 的重复计算和显存开销。

本项目没有专门实现论文的 KV-cache 管理，而是依赖远端采样服务完成每轮生成。不过，本项目实现了另一个正确性关键点：下一轮 prompt 直接拼接真实采样 token 和 observation token，不经过整段文本重编码。

二者解决的问题不同：

- **KV-cache reuse**：主要解决重复计算和吞吐效率；
- **token-in token-out**：主要解决采样 token、旧 log probability 与训练 token 的一致性。

没有显式 KV cache 复用会更慢，但如果 token 对齐仍然正确，不会因此自动改变 PPO 的数学含义。

### 7.10 模型规模与参数更新方式

论文主模型是 Qwen2.5-32B-Instruct，并在更强的 DeepSeek-R1-Distill-Qwen-32B 上做扩展实验。当前官方 recipe 同样围绕 32B 模型和多机多卡分布式训练构建。

本项目改用 Qwen3.5-4B，并通过 LoRA rank 32 更新少量低秩参数。

这带来几类差异：

- 4B 基座的推理、代码和长上下文能力不同；
- LoRA 的可调整参数空间小于全量训练；
- 更高的本项目学习率不能与全量训练学习率直接比较；
- 相同训练 step 不代表相同 token 数、样本数或计算量；
- 小模型可能更依赖原生工具协议，也可能更容易受到轨迹噪声影响。

因此，“本项目 200 steps”不能与“论文 400 steps”直接按一半训练量理解。

### 7.11 Batch、group 与训练信号规模

当前官方 DAPO/GRPO 配置使用：

```text
train batch size = 512
每题响应数 = 16
最大多轮 turns = 8
最大 response length = 16384
actor learning rate = 1e-6
```

本项目使用：

```text
每步 8 道题 × group 8 = 64 条轨迹
最多 4 次 code calls
最多 6 个 assistant turns
整条轨迹最多 8192 tokens
LoRA learning rate = 4e-5
```

较小 group 和 batch 的主要影响是：

- 组均值估计更易波动；
- 更容易出现全对或全错的 degenerate group；
- 每步探索到的工具策略更少；
- 单步成本显著下降；
- 能够先验证端到端机制是否成立。

### 7.12 8k 与 16k 轨迹预算

论文和当前官方配置使用 16k 级序列预算，本项目将整条轨迹限制为 8k。

这不仅是运行成本差异，也可能改变最终指标：

- 长数学推理更容易在最终 `\boxed{}` 前被截断；
- 多次工具调用会更快消耗剩余上下文；
- 复杂自我修正轨迹可能无法完成；
- Format 与 correct 都可能受到预算上限影响。

因此，本项目评测中的格式失败不能全部解释为模型“没学会格式”，其中一部分可能是轨迹预算不足导致的截断。

### 7.13 评测规模与统计稳定性

论文对 AIME2024 和 AIME2025 进行大量重复采样，以平均准确率估计 pass@1，并报告多种消融与基线。

本项目使用 30 道 AIME25、每题 12 次采样，且目前报告来自单次训练和单随机种子。

因此可以观察：

- Average@12 是否总体上升；
- Format 是否改善；
- 工具调用和沙箱指标是否朝合理方向变化；
- checkpoint 间是否存在明显退化。

但不能据此做强结论：

- 不能声称稳定达到论文收益；
- 不能把单次 Pass@12 波动解释成确定的能力变化；
- 不能排除随机种子、采样服务和评测规模造成的偶然性；
- 不能直接与论文 32B 模型的绝对准确率比较。

### 7.14 哪些差异最可能影响算法结论

可以按影响程度理解这些差异。

#### 高影响差异

- 跳过 cold-start SFT；
- 32B 换成 4B，并从全量训练换成 LoRA；
- 论文 PPO、官方 DAPO/GRPO 与本项目组内中心化 PPO 的 advantage 机制不同；
- 16k 缩短到 8k；
- batch、group 和总采样量大幅缩小；
- reward 是否包含工具轮次 shaping。

这些差异会改变初始策略、有效训练信号、探索范围或最终优化目标。

#### 中等影响差异

- `<code>` 标签换成原生 tool call；
- 工具轮次上限不同；
- 学习率、优化器细节和 checkpoint 频率不同；
- 单次工具返回长度和输出截断策略不同。

它们可能影响模型行为分布和训练稳定性，但不一定改变 ReTool 核心思想。

#### 主要是工程效率差异

- 分布式沙箱换成本地进程；
- 是否显式复用 KV cache；
- vLLM/veRL 分布式调度换成 PyTRIO 远端采样；
- 动态 micro-batch 的具体装箱方式。

只要语义、token 对齐和 loss mask 正确，这些差异主要影响吞吐、成本和可扩展性。不过工程问题一旦造成 observation 错位、超时偏差或 token 重编码，也会进一步变成算法正确性问题。

### 7.15 本项目“复现成功”应怎样定义

本项目的合理目标不是复制论文的绝对分数，而是分层验收。

#### 机制复现

- 模型能在推理中动态调用代码；
- observation 正确回填并影响后续生成；
- observation token 不参与 loss；
- 最终 reward 能转换为组内 advantage；
- PPO 能完成稳定更新。

#### 行为趋势复现

- 合法调用率或沙箱成功率改善；
- 正确率与格式率总体改善；
- 模型出现修改代码、利用 observation 等行为；
- 工具调用没有明显塌缩为永不调用或无脑调用。

#### 论文数值复现

这需要更接近论文的模型规模、cold-start、训练算法、16k 预算、大 batch、多随机种子和评测规模。本项目当前配置不满足这些条件，因此不应宣称完成论文数值复现。

### 7.16 全文主线总结

ReTool 的理论链路可以最终压缩为：

```text
纯文本 long CoT 在复杂计算上不可靠
→ 让代码执行进入模型推理回路
→ 生成、执行、反馈、续写形成 code-interlaced rollout
→ 只根据最终答案产生 outcome reward
→ 同题轨迹比较得到相对 advantage
→ PPO clip 稳定地调整 assistant 动作概率
→ 有益工具行为在重复选择中逐步增加
```

理解本项目时，还要附加一句限定：

> 本项目复现的是 ReTool 的核心机制与低成本训练闭环，而不是论文完整训练配方的等比例缩小版。

论文、官方 recipe 与本项目之间的差异不是附属信息，而是解释实验结果、定位故障和判断结论强度的必要部分。
